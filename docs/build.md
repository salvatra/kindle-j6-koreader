# Rebuild and verify

The build is for an **x86_64 Linux host**, not for execution on the Kindle. Requirements:
Python 3.11+, Git, a host C compiler/linker with development headers, binutils (`readelf`),
CA certificates and network access to GitHub, static.rust-lang.org and crates.io. The
script does not install packages or change the system Rust toolchain.

From the repository root:

```sh
python3 -m unittest discover -s tests -v
python3 tools/check_repo.py
python3 tools/reproduce.py
```

`--tests-only` runs the same source preparation and baseline/patched tests but skips the
ARM release build. A full run is required for ABI validation.

## Locked inputs and outputs

[sources.json](../provenance/sources.json) is the machine-readable source of truth:

- Mapper v1.6.0, commit `fa3a851ef1d26f3045ef27c7dc3465e45d56de14` and source-archive SHA256.
- Public patch SHA256 and the different historical patch SHA256.
- Official rustc, Cargo, host standard library and ARM standard library **1.98.1**,
  each pinned by URL and SHA256; the upstream Cargo.lock is retained with `--locked`.
- Build ID `fa3a851-e21-j6`, target `armv7-unknown-linux-musleabihf`, bundled rust-lld,
  and upstream `link-self-contained=yes` release profile.
- Historical installed binary and original upstream binary hashes; exact KHP .kpkg hash.

The reproducer verifies every cached download before use and rejects archive traversal,
links and special files. It recreates only its managed `build/source`, `build/baseline`
and `build/toolchain` directories; do not keep edits there. Downloads and Cargo cache
live in `.cache/`, and Cargo outputs live in `build/`. Both are ignored by Git.

The baseline copy retains the new tests but restores `direct || multitouch` classification.
Expected result: **42 pass, 3 fail**. The public patch must then produce **45 pass, 0 fail**.
The unchanged production fix adds no public mapper configuration key or HTTP API.

Outputs:

| Generated file | Meaning |
| --- | --- |
| `build/verification.json` | Actual tool versions, test results, checksum, static/ABI checks |
| `build/baseline-tests.log` | Expected three regression failures |
| `build/patched-tests.log` | All 45 tests passing |
| `build/arm-build.log`, `build/arm-elf.txt` | Build and static ELF inspection evidence |
| `build/target/armv7-unknown-linux-musleabihf/release/kindle-button-mapper` | Fresh local executable, **not deployed** |

Never run this daemon on the development host to test it. ELF inspection and unit tests
are sufficient for software validation; deployment and physical page tests are separate.

## Checksums do not mean interchangeable hardware evidence

The original installed binary was 755,692 bytes with SHA256
`f3a5f7951fab9cd07aeaeb1e3c709003b555dc5b759411488d1ac162aa8caf55`.
The first public-recipe build was 754,988 bytes with SHA256
`06672cb00e021eac28e3862e20af0240f557b7f479c85fd8b233c06c7983f741`.
Both inspections identify ELF32 ARM EABI hard-float, VFPv3-D16 and static linkage.

**The hashes differ.** The public recipe uses the bundled linker through Cargo's target
linker environment setting; the historical build supplied its local linker path in
Rust flags. Build inputs/invocation details can change byte output. We have not proven
the exact reason for every byte difference, and do not claim binary equality. The public
build passed host tests and ABI inspection; only the historical build has the recorded
physical-device results. Always use the checksum generated by your own verified build
when preparing a deployment.

The first clean [GitHub Actions build](https://github.com/salvatra/kindle-j6-koreader/actions/workflows/ci.yml)
also passed, using Ubuntu 24.04 and the same pinned Rust components. Its binary was
755,228 bytes with SHA256
`be7b1a4a5aa406115d4ffb0498d378b6e2180cc3dbafbcc7e2c89c06fc9e9fa1`.
This differs from both the Arch build and historical device binary. The recipe
reproduces the source change, tests and target build, but **byte-for-byte reproducibility
across host environments has not been established**. The host C toolchain and build paths
are not normalized. The verification snapshot retains these results separately.

The public patch changes only the fixture's personal Bluetooth identity to a synthetic
one. This changes the patch checksum, while leaving production code and gesture data
unchanged. Do not relabel the sanitized patch with the historical patch hash.

If a download or hash check fails, stop. Do not bypass it or silently choose a newer
version. Inspect the upstream change and update provenance deliberately. Public source
availability is an external dependency; this repository is not a vendored offline SDK.
